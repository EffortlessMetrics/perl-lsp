# Compiler-Backed Perl LSP Roadmap

This document defines the next semantic direction for `perl-lsp`.

The product is still the language server. The goal is not to ship a
general-purpose `rust-perl` replacement. The goal is to grow a Rust language
engine that can answer compiler-grade questions for editor features:

- What package, lexical scope, and pragma state are active here?
- Which symbols are declared by syntax, imported by compile-time rules, or
  generated by a framework?
- Which prototypes, constants, and inheritance facts affect this call?
- Which references are safe to rename, and which are behind dynamic boundaries?
- Which diagnostics are proven false positives by the semantic model?

Parsing stays the fast front lens. The path forward is to add the compiler
layers that turn syntax into durable semantic facts.

## Design Position

`perl-lsp` should be a compiler-backed LSP, not a Perl runtime host.

The primary engine is Rust:

```text
source
-> lexer
-> concrete syntax / recovery tree
-> AST
-> HIR
-> scope and pad model
-> package / stash model
-> pragma / feature model
-> import / export model
-> framework adapters
-> compile-time effect model
-> tooling IR
-> semantic fact graph
-> LSP providers
```

Real Perl still matters, but as a conformance oracle and validation instrument:

- differential tests against selected fixtures,
- framework behavior discovery,
- corpus conformance checks,
- validation of dynamic boundaries.

It must not become the normal editor hot path or a required runtime dependency
for baseline analysis. Public positioning that the parser does not call Perl is
still true for normal source analysis.

## Fast, Warm, Cold

The LSP should be organized as a tiered query engine.

### Fast Path

Runs on edits and must remain cheap:

- lexing,
- parsing,
- recovery,
- AST spans,
- local HIR refresh,
- local lexical facts,
- syntax-backed document symbols,
- fallback diagnostics and completions.

### Warm Path

Runs asynchronously and is cached by document or workspace hash:

- HIR indexing,
- lexical and package scope graphs,
- static import/export rules,
- simple inheritance,
- framework projections for stable patterns,
- workspace symbol and reference facts.

### Cold Path

Runs only when lower layers cannot honestly know the answer:

- compile-time effect modeling,
- module graph resolution,
- dynamic boundary classification,
- differential validation against sandboxed real Perl in CI or explicit proof
  lanes.

Cold-path results must be cached, provenance-tagged, and safe to ignore. A
failure in this layer must degrade answers; it must never break editing.

## Fact Doctrine

Every semantic fact should carry enough context for providers to be honest:

```text
entity id
kind
name
package / scope
range, if source-backed
provenance
confidence
source hash
dependency or module graph hash, when relevant
adapter or compiler-model version, when relevant
dynamic boundary, when unsupported behavior is observed
```

Providers should prefer exact facts but surface uncertainty instead of inventing
precision.

Suggested fact tiers:

```text
ExplicitSyntax
StaticDerived
FrameworkProjected
CompileModeled
RealPerlOracle
DynamicBoundary
```

`RealPerlOracle` is proof support, not the primary production source for editor
answers.

## Phase 0: Measurement Closeout To Capability Gaps

Parser-accuracy measurement rows are the control plane, not the finish line.
When measurement gaps are closed, status language should move to capability
gaps:

- syntax and recovery gaps,
- static semantic gaps,
- framework gaps,
- compile-time modeling gaps,
- provider behavior gaps.

Current denominators and failure packets belong in the generated parser status
files, not in this roadmap.

## Phase 1: HIR

Add a normalized high-level representation over the AST.

AST answers "what was written?" HIR answers "what language construct is this?"

Initial constructs:

- package declarations,
- subroutine and method declarations,
- `use` and `require`,
- lexical declarations,
- `our` and package declarations,
- calls and method calls,
- blocks,
- barewords,
- literals,
- dynamic boundaries.

The first HIR PR should be crate-local and fixture-backed. It should not cut LSP
providers over.

## Phase 2: Scope And Pad Model

Model Perl's lexical compilation state:

- `my`,
- `our`,
- `state`,
- `local`,
- package boundaries,
- block scopes,
- sub scopes,
- signature variables,
- pragma and feature visibility.

Outputs:

- scope frames,
- lexical bindings,
- package bindings,
- visible symbol sets,
- local reference facts.

This layer should unlock safer local rename, reference search, completions, and
diagnostics before broader compile-time modeling exists.

## Phase 3: Package And Stash Model

Model package symbol tables as first-class compiler state:

- package declarations,
- sub declarations,
- `our` variables,
- typeglob assignments,
- simple aliases,
- `@ISA`,
- constant subs,
- `AUTOLOAD` boundaries.

Outputs:

- package facts,
- stash facts,
- glob-slot facts,
- inheritance facts,
- alias facts,
- dynamic-boundary facts.

## Phase 4: Pragmas, Features, Imports, And Exports

Model common compile-time effects natively in Rust:

- `strict`,
- `warnings`,
- `feature`,
- `lib`,
- `@INC` and configured include paths,
- workspace module resolution,
- `parent`,
- `base`,
- `constant`,
- `vars`,
- `subs`,
- static `Exporter` cases,
- static `Exporter::Tiny` cases.

This phase should emit facts, not provider-specific behavior. Provider cutover
should happen only after scorecards and shadow comparisons show the facts are
stable.

This builds on the first-wave semantic substrate plan:

- [Semantic substrate first-wave plan](SEMANTIC_SUBSTRATE_FIRST_WAVE_PLAN.md)

## Phase 5: Framework Adapters

Frameworks are compile-time language extensions in practice. Stable patterns
should be modeled as explicit adapters over the fact graph:

- `Moo`,
- `Moose`,
- `Class::Tiny`,
- `Object::Pad`,
- `DBIx::Class`,
- `Catalyst`,
- `Dancer`,
- `Test::More`,
- `Try::Tiny`,
- `AUTOLOAD`-heavy modules.

Adapters emit generated-member facts, diagnostic policies, completions, and
rename blockers with provenance. They should not special-case LSP providers
directly.

## Phase 6: Compile-Time Effect Model

After HIR, scope, stash, and import/export facts exist, add a bounded model of
compile-time effects.

Start with representation and side-effect logging:

- `BEGIN`,
- `UNITCHECK`,
- `CHECK`,
- `use`,
- `no`,
- `require`,
- `import`,
- constant folding,
- prototype registration,
- symbol table mutation.

Then add safe evaluators for literal and modeled effects. Unsupported behavior
must produce a dynamic boundary, not a guessed fact.

Needed infrastructure:

- virtual filesystem and module resolver,
- modeled `@INC`,
- pragma stack,
- stash state,
- side-effect log,
- dynamic boundary packet.

## Phase 7: Tooling IR

Introduce a Perl intermediate representation oriented around editor tooling,
not bytecode execution.

It should model:

- scalar, list, and void context,
- lexical reads and writes,
- stash reads and writes,
- calls and method dispatch,
- assignment,
- branches,
- regex operations,
- dereference and glob access,
- dynamic boundaries.

The IR becomes the base for control-flow analysis, dead-code detection,
safe-delete, rename safety, and higher-confidence references.

## Sandbox And Real Perl Role

Sandboxed real Perl is still useful, but as proof infrastructure:

- differential tests,
- selected CPAN conformance checks,
- framework behavior discovery,
- validation of compiler-model disagreements,
- dynamic-boundary calibration.

Execution-bearing proof lanes must document:

- what runs,
- what it can read,
- what it can write,
- whether network is possible,
- timeout,
- memory/process caps,
- cache key,
- failure behavior.

No real-Perl execution should be hidden inside normal provider behavior.

## Metrics

Add compiler-substrate metrics as the layers appear:

- HIR lowering coverage,
- scope resolution precision,
- stash fact precision,
- import resolution precision,
- export resolution precision,
- pragma model coverage,
- prototype resolution precision,
- framework generated-member recall,
- compile-time effect model coverage,
- dynamic-boundary classification rate,
- IR lowering coverage.

Differential proof metrics should stay separate:

- Rust model vs real Perl package agreement,
- symbol table agreement,
- import/export agreement,
- `@ISA` agreement,
- prototype agreement,
- constant agreement.

## CI Shape

Fast PR lanes should stay Rust-only where possible:

```text
HIR fixtures
scope fixtures
stash fixtures
semantic scorecards
parser accuracy checks
provider shadow comparisons
```

Nightly or label-gated lanes can run differential checks against sandboxed real
Perl and selected corpus fixtures.

Any PR adding compile-time effect modeling should include:

- fact schema update,
- fixture,
- dynamic-boundary behavior,
- provider-impact statement, if any,
- differential proof or an explicit reason it is unavailable.

## Parallel Parser Work

Compiler layers do not replace parser hardening. Syntax and recovery gaps should
continue in narrow PRs:

```text
one corpus bucket
one reproducer fixture
one parser fix
one status update
one regression
```

Do not weaken gold expectations to reduce packet counts. Capability gaps should
be named and burned down, not hidden.

## Working Doctrine

```text
Fast path first.
Static facts are preferred when honest.
Framework projections promote stable dynamic patterns into cached Rust facts.
The Rust compiler substrate is the primary semantic engine.
Sandboxed real Perl is a conformance oracle, not the editor runtime.
Every fact has provenance, confidence, and freshness.
Unsupported compile-time behavior becomes a dynamic boundary.
Runtime execution is explicit, never ambient.
Provider cutover follows proof, not optimism.
```
