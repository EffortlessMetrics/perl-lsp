# Parser Scorecard

> **Status**: stood up, improvement-only (baseline floors committed; ratchet is active).
> **Umbrella issue**: [#4063](https://github.com/perl-lsp/perl-lsp/issues/4063).
> **Baseline file**: [`.ci/metrics/baselines/parser.json`](../../../.ci/metrics/baselines/parser.json).
> **Runtime status page**: [`docs/project/status/parser.md`](../status/parser.md) (regenerated by `just status-update`).
> **Scope**: everything the parser layer produces — lex, parse, error recovery, node-kind coverage, corpus cleanliness.

The parser scorecard answers the question **"can we ingest real Perl without erroring, and when we can't, do we recover usefully?"**

It is one of the seven subsystem scorecards defined in [`README.md`](README.md) and the first one to graduate from *proposed* to *stood up, improvement-only* in the scorecard lifecycle.

## 1. The four shape-questions, answered

Every scorecard in this repo answers the same four questions, in the same order:

| Question | Parser answer | Source |
| --- | --- | --- |
| **Coverage** | How much of Perl do we try to parse? Headline number: node-kind coverage (which syntactic shapes have at least one green test) + GA-feature coverage. | `corpus_audit` on the project corpus, rendered in `docs/project/status/parser.md`. |
| **Correctness** | When we try, are we right? Headline number: clean-parse rate on three separate corpora, plus strict-clean subset pass rate on the pinned manifest. | `just corpus-sweep-check`, `just cpan-corpus-check`, `just common-corpus-check`. Receipts in `.ci/parser-corpus-baseline.json`, `.ci/cpan-corpus-baseline.json`, `target/receipts/common-corpus-sweep.json`. |
| **Real-user behavior** | What does it look like on real code? Headline number: clean-parse rate on the CPAN top-1000 corpus (9 000+ files). | `just cpan-corpus-check`. |
| **Cost** | What does it cost to run? Headline numbers: cold / warm / incremental parse time on a representative file. | `cargo bench -p perl-parser --features incremental -- parse_regime`; JSON receipts under `benchmarks/results/`. |

All four rows are rendered live on [`docs/project/status/parser.md`](../status/parser.md).

## 2. Metrics catalogue

### 2.1 Floor metrics (ratchet-gated)

Floor metrics are what the ratchet (see [`README.md` §4](README.md#4-the-ratchet-model)) defends against regressions. A PR that lowers any of these below the baseline value (minus the tolerance in `.ci/metrics/baselines/parser.json`) must not merge without a conscious, reviewed baseline change.

| Floor metric | Type | Direction | Source | Notes |
| --- | --- | --- | --- | --- |
| `system_clean_rate` | ratio (0..1) | higher-is-better | `.ci/parser-corpus-baseline.json` | Clean-parse rate on the Ubuntu system Perl corpus (~7 000 files). The "compatibility" floor — defends against shipping a parser that can't parse the system Perl install. |
| `cpan_clean_rate` | ratio (0..1) | higher-is-better | `.ci/cpan-corpus-baseline.json` | Clean-parse rate on the CPAN top-1000 corpus (~9 000 files). The "ecosystem breadth" floor — defends against shipping a parser that drops popular CPAN modules. |
| `strict_clean_subset_pass_rate` | ratio (0..1) | higher-is-better | `target/receipts/common-corpus-sweep.json` | Clean-parse rate on the 10 pinned modules in `.ci/common-corpus-manifest.txt`. The "promise list" floor — smaller, strict, zero-error. |
| `system_crash_count` | count | lower-is-better | `.ci/parser-corpus-baseline.json` | Panic / crash count on the Ubuntu corpus. Must stay at zero. |
| `system_files_unreadable` | count | lower-is-better | `.ci/parser-corpus-baseline.json` | Files that could not be opened on the Ubuntu corpus. Moves only when the corpus changes. |
| `system_total_error_nodes` | count | lower-is-better | `.ci/parser-corpus-baseline.json` | Total error-node count across the Ubuntu corpus. A coarse "how many mistakes did we make?" counter. |
| `cpan_total_error_nodes` | count | lower-is-better | `.ci/cpan-corpus-baseline.json` | Total error-node count across the CPAN corpus. Same shape as above. |

The `lower_is_better` suffix rule (`_count`, `_nodes`, `_unreadable`) in [`ratchet.rs`](../../../xtask/src/tasks/metrics/ratchet.rs) matches each of these automatically.

### 2.2 Improvement metrics (tracked, not floored)

Improvement metrics are displayed on the status page and encouraged upward, but a PR that does not move them does not fail the gate. These are allowed to be `null` in the baseline until they have a stable denominator.

| Improvement metric | Source | Next step |
| --- | --- | --- |
| `node_kind_coverage` | `corpus_audit` project-corpus summary | Candidate for floor once the denominator (`NodeKind` total) has been stable across two releases. |
| `error_density_per_1k_loc` | not yet instrumented | [#4063 PR 2 plan](https://github.com/perl-lsp/perl-lsp/issues/4063#issuecomment-4229331588): count lines in `parser_corpus_sweep` and divide by `total_error_nodes`, median over dirty files. |
| `recovery_salvage_rate` | not yet instrumented | Follow-up issue after the first scorecard ships. Requires a malformed-fixture bank under `crates/perl-corpus/fixtures/malformed/` or equivalent. |

### 2.3 Cost metrics: cold / warm / incremental regimes

The three parse regimes are measured by the `parse_regime` Criterion group in [`crates/perl-parser/benches/incremental_benchmark.rs`](../../../crates/perl-parser/benches/incremental_benchmark.rs):

| Regime | Benchmark | What it measures |
| --- | --- | --- |
| **Cold** | `bench_full_reparse` | Fresh `IncrementalState::new(source)` — allocator, rope, line index, tokens, AST, checkpoints all allocated from scratch. |
| **Warm** | `bench_warm_reparse` | `apply_edits(&mut state, &[])` on a pre-allocated `IncrementalState` — the warm full-reparse fallback path, measuring reparse cost without cold-start allocations. |
| **Incremental** | `bench_incremental_small_edit` | `apply_edits` with a single small edit — the checkpoint-driven incremental path. |

Run them together with:

```bash
cargo bench -p perl-parser --features incremental -- parse_regime
```

The three regimes are grouped so their Criterion estimates land in sibling directories under `target/criterion/`, making cold-vs-warm and warm-vs-incremental ratios easy to read off a single run. This mirrors the pyright phase-timing lesson and the rust-analyzer / gopls cold-vs-warm separation documented in [#4099](https://github.com/perl-lsp/perl-lsp/issues/4099).

The invariant that `apply_edits(&mut state, &[])` actually takes the full-reparse path is guarded by `test_apply_edits_empty_slice_full_reparses` in [`crates/perl-incremental-parsing/src/incremental/mod.rs`](../../../crates/perl-incremental-parsing/src/incremental/mod.rs) — if that test ever fails, the warm benchmark is silently no longer measuring the reparse regime.

## 3. How the baseline gets updated

The baseline file is at [`.ci/metrics/baselines/parser.json`](../../../.ci/metrics/baselines/parser.json). It has the shape defined by `SubsystemBaseline` in [`ratchet.rs`](../../../xtask/src/tasks/metrics/ratchet.rs):

```jsonc
{
  "schema_version": 1,
  "measured_at": "2026-04-09T18:13:43Z",
  "subsystem": "parser",
  "commit": "3f7ede36",
  "floor_metrics":       { ... },
  "improvement_metrics": { ... },
  "tolerance_pct": 0.005
}
```

The ratchet runs via:

```bash
cargo xtask metrics ratchet-check --subsystem parser --current target/metrics/parser.json
```

A baseline **raise** is allowed only after the new value has been stable across the stability window defined in the scorecard lifecycle ([`README.md` §4](README.md#4-the-ratchet-model)). A baseline **lower** requires a conscious PR explaining the root cause; the ratchet will not do this automatically.

## 4. Which crates feed the parser scorecard

Primary (feature work lands here):

- `perl-parser` (composition)
- `perl-parser-core` (recursive-descent engine, error recovery)
- `perl-lexer` (context-aware tokenizer)
- `perl-ast`, `perl-ast-v2` (AST types)
- `perl-token` (token types)
- `perl-quote`, `perl-regex`, `perl-heredoc` (lexical sub-layers)

Secondary (contribute cost numbers but not feature gates):

- `perl-incremental-parsing` — owns the cold / warm / incremental benchmarks.
- `xtask` — owns the sweep drivers and the ratchet checker.

A change outside the primary list that moves a parser floor is usually an indication that the crate boundary needs revisiting; flag it in the PR so an architecture reviewer can weigh in.

## 5. How to file work against this scorecard

If your PR changes the parser, the description should answer:

- **Which floor metric does this move?** If none, say "improvement-only" and call out the improvement metric.
- **Is this a floor raise?** If yes, attach N consecutive run receipts (see [`README.md` §4](README.md#4-the-ratchet-model)) and update `.ci/metrics/baselines/parser.json` in the same PR.
- **Which regime does this affect?** Cold / warm / incremental / all. Benchmarks for the affected regime must be green.

If you are unsure whether a change belongs on the parser scorecard or the engineering-health scorecard ([#4070](https://github.com/perl-lsp/perl-lsp/issues/4070)): parser owns **parser-output correctness and cost**; engineering-health owns **cross-subsystem reliability** (mutation, flaky tests, latency roll-ups). A change to the recursive-descent parser is parser. A change to the mutation harness is engineering-health.

## 6. What's explicitly out of scope

- **Recovery salvage rate** is listed in §2.2 but not yet instrumented. Tracking is in [#4063](https://github.com/perl-lsp/perl-lsp/issues/4063).
- **Lex-phase timing separated from parse-phase timing** requires instrumentation in `perl-lexer` and is tracked as a TODO in [`xtask/src/tasks/parser_corpus_sweep.rs`](../../../xtask/src/tasks/parser_corpus_sweep.rs).
- **Per-file timing roll-ups** (slowest-20 report) are owned by `cargo xtask metrics parser-stats`; see [`xtask/src/tasks/metrics/parser_stats.rs`](../../../xtask/src/tasks/metrics/parser_stats.rs).
