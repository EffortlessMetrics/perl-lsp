# Building a Production LSP Server with AI Agents: A Case Study

> How the perl-lsp project grew from 2 crates to 121, from 248 commits to 2,100+,
> and from a tree-sitter experiment to a production-ready Perl language server --
> with AI agents doing the bulk of the work.

---

## Introduction

The perl-lsp repository tells a remarkable story about what happens when AI coding
agents become the primary development force behind a real software project. What
started in July 2022 as a modest tree-sitter grammar for Perl evolved into a
121-crate Rust workspace providing a full Language Server Protocol implementation,
Debug Adapter Protocol support, and a recursive descent parser with near-complete
Perl 5 syntax coverage.

The twist: the vast majority of this work was done by AI agents -- primarily
OpenAI's Codex and Anthropic's Claude Code -- operating under human supervision
but producing code at a pace that no single developer could match. The project
serves as both a successful product and a living experiment in agentic software
development.

This article examines the evidence, patterns, and lessons from that experiment.

## The Development Model

### Three Agents, One Repository

The repository shows evidence of at least three distinct AI agent families
contributing:

1. **OpenAI Codex** -- The most visible. Branch names prefixed with `codex/` are
   auto-generated by the Codex agent, with descriptive slugs and random suffixes
   (e.g., `codex/split-and-integrate-srp-microcrates-kzvaqa`). 203 remote branches
   and 266 PRs carry this prefix.

2. **Anthropic Claude Code** -- Guided by the `CLAUDE.md` file (282 lines of
   detailed instructions), Claude Code operates on the repository with explicit
   coding standards, banned constructs, and architectural constraints.

3. **Google Jules** -- 22 commits on master from `google-labs-jules[bot]`,
   contributing performance optimizations and security fixes with distinctive
   commit prefixes like "Bolt:" (performance) and "Sentinel:" (security).

4. **Dependabot** -- 34 automated dependency update commits, configured via
   `.github/dependabot.yml`.

### The Human Role: Architect and Gatekeeper

The contributor log shows that the human maintainer (Steven Zimmerman) accounts
for the overwhelming majority of merged commits (~1,860 of ~2,100 on master).
But the commit messages, branch patterns, and PR velocity make clear that much
of this is agent-generated code merged under the human's account. The human's
role shifted from writing code to:

- Setting architectural direction (tier system, crate families, SRP extraction strategy)
- Writing and refining agent instructions (CLAUDE.md, AGENTS.md)
- Designing CI gates that mechanically enforce quality standards
- Reviewing and merging agent-generated PRs
- Handling the cases where agents get stuck or produce incorrect results

## CLAUDE.md: Teaching an Agent How to Work

The `CLAUDE.md` file is a 282-line instruction manual for AI agents. It evolved
through at least 30 revisions (tracked in git history from August 2025 onward) and
represents a sophisticated approach to agent guidance. Key sections include:

### What It Teaches

- **Build commands**: Exact cargo invocations for building, testing, and linting
- **Crate structure**: A tier system from leaf crates (Tier 1) through application
  binaries (Tier 6) to legacy crates (Tier 7)
- **Coding standards**: Explicit bans on `unwrap()`, `expect()`, `panic!()`,
  `todo!()`, `unimplemented!()`, and `dbg!()` in production code, with alternatives
  specified for each
- **Architecture patterns**: The dual-indexing pattern for function references,
  threading configuration for LSP tests
- **CI gate tiers**: Three tiers (pr-fast, merge-gate, nightly) with time budgets

### Companion Files

The project also maintains:

- **AGENTS.md** (213 lines) -- A broader, less Claude-specific agent guide with
  project overview and development guidelines
- **.github/copilot-instructions.md** -- Adapted from CLAUDE.md for GitHub Copilot
- **features.toml** (953 lines) -- Machine-readable LSP capability catalog that
  agents can query

The key insight: the project treats agent instruction files as first-class
source code, versioned and reviewed like any other file. CLAUDE.md has been
updated 30+ times, evolving alongside the codebase it describes.

## Branch and PR Patterns: The codex/ Convention

### Naming Pattern

Codex agent branches follow a consistent pattern:
```
codex/<verb>-<noun-phrase>[-<random-suffix>]
```

Examples from the repository:
- `codex/split-and-integrate-srp-microcrates-kzvaqa`
- `codex/convert-panic-branches-to-return-errors`
- `codex/implement-file-completion-logic`
- `codex/find-and-fix-an-issue-i8frdj`

The random suffix (like `-kzvaqa`) disambiguates when the same task is attempted
multiple times. This is visible in the SRP extraction campaign, where branches
like `codex/split-and-integrate-srp-microcrates-*` appear with 30+ different
suffixes, revealing a pattern of repeated attempts until the agent produces
work that passes the CI gate.

### The Failure Rate

Of the 266 PRs from `codex/` branches:
- **146 merged** (55%)
- **112 closed without merging** (42%)
- **8 open** (3%)

A 42% rejection rate is significant. Examining the closed PRs reveals many are
duplicate attempts at the same extraction task -- the agent would produce a PR
that failed CI or had structural problems, so it would be closed and a fresh
attempt started on a new branch. This trial-and-error approach, mediated by CI
gates, is a defining characteristic of agentic development.

## The SRP Extraction Campaign: 2 Crates to 121

The most dramatic evidence of agentic development is the crate explosion. The
repository went from **2 crates** (tree-sitter-perl-c, tree-sitter-perl-rs) in
June 2025 to **121 crates** by March 2026.

### Timeline

| Date | Crate count | Milestone |
| ---- | ----------- | --------- |
| Jun 2025 | 2 | Pre-agent era |
| Sep 2025 | 10 | Initial LSP/parser crate separation |
| Oct 2025 | 7 | Some consolidation |
| Jan 2026 | 8 | Still relatively monolithic |
| Feb 2026 | 46 | **Microcrate extraction begins** |
| Mar 2026 | 121 | Full SRP decomposition |

The leap from 8 to 46 crates in February and then to 121 in March 2026
represents a systematic extraction campaign. The commit messages reveal the
pattern:

1. **Identify**: Find a module with distinct responsibility within a larger crate
2. **Extract**: Move it to a new crate with its own `Cargo.toml`
3. **Re-export**: Maintain backward compatibility via re-exports
4. **Integrate**: Update all dependents to use the new crate
5. **Test**: Ensure CI passes with the new structure

Examples of extracted microcrates:
- `perl-lsp-uri` -- URI parsing extracted from the LSP server
- `perl-lsp-input-validation` -- Request validation logic
- `perl-dap-security` -- DAP security validation
- `perl-lsp-folding` -- Folding range computation
- `perl-workspace-ignore` -- Workspace ignore rules
- `perl-line-index` -- Line/column offset computation
- `perl-lsp-completion-item` -- Completion item types
- `perl-content-length-framing` -- LSP message framing

124 PRs across the project's history reference microcrate extraction, SRP
separation, or similar structural refactoring in their titles. This was not a
one-time architectural decision -- it was an ongoing campaign driven by agents
following a consistent pattern.

## Guardrails: CI as the Agent Safety Net

The most sophisticated aspect of this project's agentic development model is how
CI serves as mechanical quality enforcement. The `.ci/gate-policy.yaml` file
(844 lines) defines a comprehensive multi-tier gate system that functions as the
primary quality control mechanism -- replacing traditional human code review for
routine changes.

### Gate Tiers

| Tier | Command | Time Budget | Purpose |
| ---- | ------- | ----------- | ------- |
| **A (PR-fast)** | `just pr-fast` | <3 min | Catch obvious issues |
| **B (Merge gate)** | `just ci-gate` | <8 min | Full verification before merge |
| **C (Nightly)** | `just ci-full` | <60 min | Deep testing, metrics |
| **D (Release)** | Release gate | <10 min | Release candidate validation |

### What the Gates Enforce

The merge gate includes 12 distinct checks:

1. **Format** (`cargo fmt --check`) -- Style consistency
2. **Clippy core** -- Fast lint on core crates
3. **Clippy full** -- Workspace-wide linting with strict settings
4. **Unit tests** -- All library tests across the workspace
5. **LSP smoke tests** -- Protocol basics, capabilities
6. **LSP behavioral tests** -- Definitions, completions, security
7. **Common corpus clean** -- Pinned Perl modules must parse error-free
8. **Security audit** (`cargo audit`) -- Known vulnerability check
9. **Policy checks** -- Documentation baseline, features invariants
10. **Docs build** -- Documentation compiles without errors
11. **V2 parity** -- Legacy parser compatibility verification
12. **Nested lockfile check** -- Prevents accidental nested Cargo.lock files

### The No-Unwrap Policy

Perhaps the most distinctive guardrail is the ban on `unwrap()` and `expect()` in
production code. PR #559 ("Burn down unwraps to ZERO (Phase Final)") systematically
eliminated every instance, and clippy is configured to reject new ones:

```yaml
command: >-
  cargo clippy --workspace --bins --locked --no-deps
  -- -D clippy::unwrap_used -D clippy::expect_used
```

This is explicitly designed to prevent a common agent failure mode: AI agents
frequently reach for `unwrap()` as the path of least resistance. By making this a
compile-time error, the project forces agents to handle errors properly.

The complete list of banned constructs:
- `unwrap()`, `expect()` -- use `?`, `.ok_or_else()`, or pattern matching
- `panic!()`, `todo!()`, `unimplemented!()` -- return `Result`/`Option`
- `std::process::abort()` -- never use
- `dbg!()` -- use `tracing::debug!`

### The Debt Ledger

The `.ci/debt-ledger.yaml` system provides a structured way to manage technical
debt with explicit budgets:

- Maximum 10 quarantined tests
- Maximum 20 known issues
- Maximum 30 technical debt items
- Warning threshold at 80% of budget

This prevents the common failure mode where agents generate code that works but
accumulates hidden quality debt. The debt budget is enforced mechanically -- if
exceeded, the merge gate fails.

### Escape Hatches

The gate policy includes documented escape hatches for emergencies, with
escalating severity:

1. **Skip a gate**: `[skip-gate:GATE_NAME]` in commit message (logged to audit trail)
2. **Force merge**: Requires two maintainer approvals + justification
3. **Disable all gates**: Nuclear option, requires admin, auto-reverts after 24 hours

The existence of formal escape hatches is itself revealing -- it acknowledges that
rigid gates can sometimes block legitimate urgent changes, while ensuring that
bypasses are logged and tracked.

## Quality Metrics Under Agentic Development

### The Test Explosion

The test coverage expansion is one of the clearest signals of agent-driven
development. On March 4, 2026 alone, 126 test PRs were created, adding
comprehensive unit tests to dozens of crates. The commit messages follow a
formulaic pattern:

```
test(CRATE_NAME): add comprehensive unit tests
test(CRATE_NAME): add extended unit tests
```

This systematic, batch-oriented approach to test generation is a hallmark of
agentic development -- a human developer would typically add tests incrementally
alongside feature work, not in a single massive campaign.

### Computed, Not Claimed

The project enforces a "computed, not hand-edited" philosophy for metrics:

- `CURRENT_STATUS.md` is auto-generated by `scripts/update-current-status.py`
- `features.toml` is the canonical source for LSP capabilities
- `just status-check` fails if documentation drifts from computed values
- CI receipts (test output, gate output) serve as evidence for all claims

This addresses a known weakness of agent-generated documentation: AI agents
confidently produce metrics that may be fabricated. By requiring that all metrics
be computed from source, the project prevents false claims from entering the record.

### Key Quality Indicators

| Metric | Value | Enforcement |
| ------ | ----- | ----------- |
| Mutation testing score | 87% | Nightly gate |
| Production unwrap/expect count | 0 | Compile-time clippy error |
| Production panic/todo/unreachable count | 0 | Compile-time clippy error |
| Explicit unsafe blocks | 0 | Tracked ratchet |
| LSP protocol compliance | 100% (97/97) | `features.toml` + tests |
| LSP user-visible coverage | 100% (53/53) | `features.toml` + tests |
| Test-to-code ratio | 1.5:1 | Organic outcome |

## Lessons Learned

### What Works

1. **Mechanical quality gates are essential**. Without `ci-gate`, agent output
   would be untrustworthy. The gates serve as the reviewer that never gets tired.

2. **Banning dangerous constructs at compile time** prevents agents from taking
   shortcuts. `unwrap()` bans force proper error handling.

3. **Agent instruction files (CLAUDE.md) are living documents** that must evolve
   with the codebase. The 30+ revisions of CLAUDE.md show ongoing refinement.

4. **Agents excel at systematic, repetitive tasks**: test generation, SRP
   extraction, dependency updates, and code migration.

5. **The retry-until-pass model works** for well-defined tasks. Give the agent a
   clear objective, let it try, check with CI, and retry if it fails.

6. **Computed metrics prevent hallucinated claims**. Never let agents write
   metrics -- make them compute metrics from source.

### What Does Not Work

1. **Agents produce verbose, sometimes redundant commit messages**. The
   "comprehensive" pattern and inflated descriptions are a persistent style issue.

2. **High rejection rates** (42% of Codex PRs closed without merge) represent
   wasted compute. Better prompting or pre-flight checks could reduce this.

3. **Agent-generated documentation can drift from reality** unless mechanically
   verified. The project learned this the hard way and built `status-check`.

4. **Architecture decisions still require human judgment**. The agents execute
   the SRP extraction pattern well, but deciding *what* to extract and *when*
   remains a human responsibility.

5. **Multi-agent coordination is manual**. There is no automated orchestration
   between Codex, Claude, and Jules -- the human maintainer serves as the
   integration layer.

## Conclusion

The perl-lsp project demonstrates that AI agents can be the primary development
force behind a production-quality software system, provided the right guardrails
are in place. The combination of CLAUDE.md (agent instructions), ci-gate
(mechanical quality enforcement), and a clear architectural vision (SRP
microcrates, tiered dependencies) created an environment where agents could
produce substantial amounts of code while maintaining quality standards.

The numbers are striking: 1,856 commits in 9 months, 119 new crates, 477,000
lines of Rust, 1,681 passing tests, 100% LSP protocol compliance. But the real
innovation is not the velocity -- it is the system of constraints that makes the
velocity sustainable.

The project's `AGENTIC_DEV.md` sums it up: "This repo is AI-native:
high-throughput changes are verified by mechanical gates, not manual inspection."
The key insight is that the scarce resource is not code production -- it is human
attention. Every guardrail, every automated check, every computed metric is
designed to minimize the human attention required per change while maximizing the
confidence in that change.

For teams considering agentic development, perl-lsp offers a concrete blueprint:
invest in mechanical verification, ban dangerous shortcuts at the language level,
treat agent instruction files as first-class source code, and accept that a
significant percentage of agent output will be rejected -- but that the successful
output, filtered through rigorous gates, can be reliable enough to ship.
