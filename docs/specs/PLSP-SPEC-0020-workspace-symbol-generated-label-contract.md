## Current Implementation Status

Workspace symbols are `partial-live-with-fallback`. Fresh ready-index
source-backed symbols may answer live. A bounded generated-label pilot may also
return source-backed generated/framework members for non-empty queries.

The pilot is virtual and labeled. Current live output uses an explicit
`[generated/framework]` marker in the symbol name and container. That label is
the current user-visible boundary: it tells the user the member is generated
from a source-backed framework declaration, not an exact generated method body.

This spec does not broaden generated workspace-symbol behavior.

## Contract

Generated/framework symbols may appear in live workspace-symbol results only
when all of these are true:

- the query is non-empty
- the workspace index is ready and fresh
- the fact is high confidence
- the fact is source-backed generated/framework evidence
- a framework declaration source anchor exists
- the result carries an explicit generated/framework label
- generated/no-source, stale, dynamic, low-confidence, ambiguous, partial-index,
  and open-document fallback candidates remain gated

Generated/framework workspace symbols must not claim exact generated method-body
locations.

## Label Contract

The current required label is:

```text
[generated/framework]
```

It may appear in the symbol name, container name, or a future structured
generated-symbol field. A future richer label may add framework and declaration
detail, such as:

```text
<name> - generated by <Framework> from <declaration>
```

Any richer label must remain explicit and must not remove the generated
boundary.

## Source Anchor Rules

`SourceBackedGenerated` workspace symbols must anchor to the source declaration
that generated the virtual member, for example:

- `has name => (...)`
- `Class::Tiny` attribute declaration
- framework route declaration
- other reviewed framework declaration forms

The anchor is not an exact generated method-body range. Providers must not use
the anchor to imply edit-safe generated implementation text.

## Blocked Classes

These classes must not appear as live generated workspace-symbol results:

- generated/no-source candidate
- dynamic generated candidate
- stale generated fact
- low-confidence generated fact
- ambiguous generated identity
- partial-index fallback candidate
- open-document fallback candidate unless a later spec proves that class
- exact generated method-body claim

They may appear in receipts as blocked, fallback, or explanation-only evidence.

## Policy Registry

The advisory registry in
[workspace-symbol-classes.toml](../../policy/workspace-symbol-classes.toml)
records the current live and blocked workspace-symbol classes. Unlisted
generated classes remain blocked or deferred until a policy row and receipt
promote them.

## Valid PR Shapes

Valid PRs under this spec include:

- adding a generated-symbol class row with source-anchor and label rules
- adding a generated/no-source blocker receipt
- adding rank/noise proof for one generated class
- adding edit-freshness proof for one generated class
- adding a validator for workspace-symbol class policy
- support-review PRs that keep generated workspace symbols virtual and labeled

Every generated-symbol PR must name the fact class, source-anchor rule, label
rule, fallback rule, blocker rule, and receipt.

## Invalid PR Shapes

Invalid PRs include:

- broad generated workspace-symbol promotion from one generated-label receipt
- generated/no-source symbols appearing as live results
- dynamic generated symbols appearing as live results
- stale or low-confidence generated symbols appearing as live results
- exact generated method-body locations
- removing or hiding generated labels
- promoting generated workspace-symbol proof into rename or safe-delete
  authorization

## Acceptance

A workspace-symbol generated-label PR satisfies this spec when:

- live generated results are fresh, high confidence, source-backed, and labeled
- the source anchor is a framework declaration
- generated/no-source, dynamic, stale, low-confidence, ambiguous, partial-index,
  and open-document fallback candidates stay gated
- rank/noise receipts show generated labels do not swamp source-backed exact
  symbols
- provider decision receipts expose the generated, fallback, or blocker state
- support-tier wording remains `partial-live-with-fallback`

Docs-only changes to this spec or policy may use:

```bash
cargo xtask check-provider-confidence-matrix

```

Class-behavior PRs must add or update focused workspace-symbol runtime
receipts for the touched class.

## Future Validator

A future validator may be exposed as:

```bash
cargo xtask check-workspace-symbol-classes
```

That validator should check:

- every live generated-symbol class has a policy row
- every generated live row requires an explicit label
- every generated live row requires a source declaration anchor
- generated/no-source and dynamic rows are blocked
- status docs and policy do not disagree on live generated classes
- blocker names align with the provider promotion ledger blocker registry

## Non-goals

- No provider behavior change from this spec alone.
- No broad generated workspace-symbol cutover.
- No generated/no-source live result.
- No exact generated method-body claim.
- No rename or safe-delete authorization from generated-symbol proof.
- No support-tier promotion from this spec alone.

## Claim Boundaries

This spec may claim that generated workspace symbols are governed by explicit
label and source-anchor rules. It may not claim broad generated-symbol support,
exact generated source locations, or edit authorization for generated members.
