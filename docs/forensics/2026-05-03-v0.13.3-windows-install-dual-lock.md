# 2026-05-03 — v0.13.3 Windows Install Dual-Lock Incident

**Lens**: One symptom, two architecturally distinct bugs, both required to ship a working fix.
**Outcome**: Shipped v0.13.3 with combined retry-budget extension + versioned managed install dirs. 25 unit tests added that split the failure modes apart for future attribution.

## Symptom

Windows users reported `Failed to obtain a Perl LSP binary` when running `Perl: Reinstall Server Binary`. The actual error in the extension output channel:

```
EBUSY: resource busy or locked, copyfile
  'C:\Users\...\Temp\perl-lsp-XXXXXX\extracted\perllsp-0.13.1-...\perllsp.exe'
  -> 'C:\Users\...\globalStorage\effortlessmetrics.perl-lsp-rs\bin\win32-x64\perllsp.exe'
```

Hosted CI (`vscode-managed-binary-smoke.yml` on `windows-latest`) had been green for some time. The PR that originally hardened this path (`#7862`) had passed CI before merging.

## First hypothesis (incomplete)

The destination perllsp.exe was held by a running language server. The fix would be to either retry longer or install to a path that doesn't conflict with the running binary.

This was correct, but only for *one* of the two failure modes.

## Local reproduction

Running the source smoke (`npm run test:integration`) on a real Windows 11 machine with Defender enabled and default exclusions:

- **First reinstall** consistently failed with EBUSY on the source path (the freshly extracted `perllsp.exe` in `%TEMP%`).
- The destination didn't exist yet — this was a clean install, no prior `perllsp.exe` in `globalStorage`.
- The lock was on the **source**, not the destination.

The retry budget at the time was `[100, 250, 500, 1000, 2000]ms` — about 4 seconds total. Defender's first-time signature scan on a fresh unsigned `.exe` regularly takes longer than that.

This was a different failure mode than the destination-lock hypothesis.

## Second reproduction (the destination-side bug)

After extending the retry budget, the first reinstall succeeded. The smoke test then tried to:

1. Run reinstall #1 → succeeded
2. Spawn `perllsp.exe` directly via `child_process.spawn` to hold the destination
3. Run reinstall #2 → **failed with EBUSY**, retry budget exhausted

Even with ~31 seconds of retries, copyFileSync cannot overwrite an executable held by a running process on Windows. The retry budget is irrelevant for this failure mode — the lock will be held forever (or until the process exits).

This was the second, distinct bug. The fix had to be architectural, not just timing: install to a *new path* rather than overwriting the running binary.

## The combined fix

Two separate but coordinated changes in `vscode-extension/src/downloader.ts`:

### 1. Extended retry budget (addresses source-side AV scan)

```typescript
const MANAGED_INSTALL_RETRY_DELAYS_MS = [100, 250, 500, 1000, 2000, 4000, 8000, 16000];
const TRANSIENT_MANAGED_INSTALL_ERROR_CODES = new Set(['EBUSY', 'EPERM', 'EACCES', 'ETXTBSY']);
```

Total retry wait grew to ~31 seconds, covering the upper end of Defender first-time scan windows.

### 2. Versioned managed install dirs (addresses destination-side running-binary lock)

Each install now lands in `globalStorage/.../bin/<platform>-<arch>/<tag>-<iso-stamp>/`. The active install is selected by an atomically-committed `current` pointer file (temp+rename). A forced reinstall while `perllsp.exe` is held by a running process now installs to a **fresh sibling dir** instead of trying to overwrite the running file. Legacy flat-layout installs are grandfathered through `getLocalBinaryPath()` until the next reinstall promotes them to a versioned dir.

Both fixes shipped in `#7870`. The release-prep landed in `#7872`. The release published as v0.13.3.

## How the smoke test masked one half

The smoke test originally written to validate the fix:

```typescript
// First reinstall
const reinstall1 = await vscode.commands.executeCommand('perl-lsp.reinstall');
// Spawn perllsp.exe to hold the destination
const lockingProcess = spawn(reinstall1.serverPath, [], ...);
await delay(750);
// Second reinstall — must succeed even though perllsp.exe is held
const reinstall2 = await vscode.commands.executeCommand('perl-lsp.reinstall');
```

When the first reinstall succeeded (because of the extended retry budget) and the second succeeded (because of versioned dirs), the test passed.

But: the test could not distinguish between the two fixes. If the retry budget regressed but versioned dirs stayed correct, the second reinstall would still pass (no source-lock during the second install because Defender's scan cache is now warm for the binary). The smoke would say "fix is working" even with the source-side regression.

This was caught only because of local reproduction on a cold-cache machine. Without it, future regressions of the source-side retry budget would have been silent until users complained.

## The test split

PR `#7874` added 25 unit tests that **split the failure modes apart**:

- **Long-tail retry budget tests** (4): assert the budget covers 8 transient failures, all four error codes are retried, exhaustion surfaces the right error.
- **Versioned managed install layout tests** (14): pointer reading, sanitization (rejects `..`, separators, missing target, empty), atomic commit (temp+rename), prune (keeps current + 1 prior, never deletes current, ignores legacy flat files), unique-name generation, **end-to-end legacy migration** (flat → versioned + atomic pointer promotion).
- **Singleflight tests** (6): ensure+ensure joins, force+force joins, force-during-ensure waits-then-runs, settle cleanup, failure recovery, force-after-force separate installs.
- **Migration test** (1): seed a flat-layout binary, simulate a versioned install, verify pointer promotion and legacy-binary preservation.

After this PR, future regression of any single mechanism is independently detectable. The smoke proves the integrated user path; the unit tests attribute breakage to the right fix.

## Lessons

1. **One symptom may be two bugs.** Especially with platform-specific failure modes. The first hypothesis is rarely the complete picture.
2. **Local reproduction matters more than CI for install paths.** Hosted runners have aggressive AV exclusions and pre-warmed signature caches that real users don't. See `docs/articles/CI_VS_REAL_USER_PARITY.md`.
3. **System tests prove the path; unit tests attribute breakage.** When fixes for distinct failure modes coexist, only unit tests can tell you which fix regressed if the system test fails.
4. **The smoke that proves the fix may not test the right surface.** Verify what the test actually exercises, especially for tests that gate releases.
5. **Architectural fixes (versioned dirs) and tactical fixes (longer retries) can be required *together*.** Versioned dirs alone don't fix source-lock; longer retries alone don't fix destination-lock. Don't ship half a fix.
