## 1. Lane doctrine is reactive unless pre-loaded

Verify `docs/reference/LANE_BOUNDARIES.md` is current before the first PR opens in a
multi-lane session — not after the first boundary violation.

**Why:** `LANE_BOUNDARIES.md` was filed during interference between lane 3 (control-plane
cleanup) and lane 6 (0.15.1 latency), not before it. Codex (lane 3) was closing lane 6 PRs
under a "burn-down" heuristic. The doc was created reactively; the interference had already
happened.

**How to apply:** Orchestrator session-start checklist: (a) confirm LANE_BOUNDARIES.md
exists and its "Lane numbers" table reflects the active lanes for this session, (b) add the
current session's lanes to that table before spawning the first builder. Two minutes at
session start prevents one hour of cross-lane cleanup.

## 2. Bare `expect()`/`unwrap()` in tests slipped past the existing lints — gap mechanism unknown

PROVISIONAL — the workspace already denies `unwrap_used` and `expect_used` (`Cargo.toml`
`[workspace.lints.clippy]`, added in PR #221). Despite that, reviewer round-trips on lane
PRs cited bare `unwrap()`/`expect()` in tests. The mechanism that let them through is not
yet identified.

**Why:** Lane reviewer threads on multiple code PRs cited bare `unwrap()`/`expect()` in test
code. The naive reading was "rule exists but isn't enforced" — but workspace-level clippy
lints ARE enforced. So the actual gap is one of: (a) the CI tier that runs on PRs
(`just pr-fast`) doesn't lint test targets, (b) builders pushed without running pr-fast, (c)
the offending tests had `#[allow(clippy::unwrap_used)]` escape hatches, or (d) reviewers
caught them visually before the clippy gate ran. Each of these is a different fix.

**How to apply:** Filed as follow-up investigation — re-read lane PR review threads to
identify which mechanism was actually at play, then file a targeted fix. Until that
investigation lands, don't claim a generic "enforcement is missing" lesson here.

## 3. Substrate PR claim discipline — "stored but unconsumed"

When a PR adds infrastructure that later PRs will consume, the PR body must say
"stored but unconsumed pending PR N" rather than implying the full wiring is live.

**Why:** PR #279 (RuntimeTuning substrate) shipped before the consumers (#280 scheduler
cancellation, #287 eager-indexing gate) landed. The maintainer held #279 in draft because
the body's framing implied the feature was fully wired. The fix was a one-line body update;
the draft hold added half a lane cycle of latency.

**How to apply:** Builder rule: when your PR adds a struct/type/field that is _not yet
called_ from any production path, include "Wired: no (pending PR N)" in the PR body's
Fix line. Maintainer and reviewer should look for this on any "substrate" PR.

## 4. CI concurrency-group cancellations are infra noise

`Canceling since a higher priority waiting request for CI-<N> exists` is not a gate
failure. Classify it as infra noise and do not route to pr-responder.

**Why:** This message appeared during the 0.15.1 lane merge sequence and was investigated
as a potential CI failure. It is GitHub Actions' concurrency-group scheduler replacing an
older queued run with a newer one — expected behavior on rapid pushes. False
classification would have routed PRs to pr-responder unnecessarily.

**How to apply:** Green-ci agent: if the only failing check contains the string
`Canceling since a higher priority waiting request`, classify as infra-noise and sign off
with a note rather than applying `needs-ci-fix`. Add this string to any CI false-positive
classifier.

## 5. Force-push rebase on a stack member — close+reopen with clean history

When a stacked PR's base branch is deleted or rebased, the correct recovery is:
close the PR, create a new branch from the current base, cherry-pick the commits,
open a new PR with `Closes #N (reopened)` in the body.

**Why:** PRs #281 and #283 (the originals) were replaced by #286 and #287 after their
base branches were superseded. The reopen pattern produced clean history, no merge-commit
noise, and preserved the issue linkage. Attempting an in-place force-push to the original
PR branch on a stacked PR causes the diff to include the base's history.

**How to apply:** Standard recovery — not an emergency procedure. When instructed to
"replace PR N," use this pattern:
```
git checkout -b <new-branch> <current-base>
git cherry-pick <commits from old branch>
git push origin <new-branch>
gh pr create --title "..." --body "... Replaces #N (Closes #N)"
```

## 6. `actions/checkout@v6` advisory — methodology-gate flake

`actions/checkout@v6` emits advisory warnings in methodology-gate that look like
failures but are not blocking. Classify as infra noise.

**Why:** Observed during the 0.15.1 lane CI runs. The advisory does not fail the check;
it appears in the log output and can look like a gate failure to an automated classifier.

**How to apply:** Green-ci and pr-responder: before applying `needs-ci-fix` on a
methodology-gate result, confirm the check's *conclusion* is `failure`, not just that
the log contains advisory text. A check with conclusion `success` and advisory log lines
is a passing check.

## 7. Factory-droid idempotency gap on reopen cycles

Factory-droid re-posts its full review set on every close/reopen. Add an idempotency
guard: if factory-droid already posted a finding set for the current diff SHA, skip.

**Why:** PRs #281/#283 were closed and reopened as #286/#287. Factory-droid ran 5–8
full review passes per PR across the reopen cycles, producing duplicate comments on
identical findings. This inflated the review queue and required manual de-duplication.
The guard is an infra improvement, not a process change.

**How to apply:** This is a factory-droid configuration issue, not a pipeline routing
issue. Filed as a follow-up (see issue tracker). Until fixed: pr-responder should
check for duplicate factory-droid findings before routing on them — if the same finding
appears verbatim from a prior pass, it has already been evaluated.
