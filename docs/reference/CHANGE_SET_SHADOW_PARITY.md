# Change-set shadow-parity report — shell selector vs `ci_scope` classifier

**Status: MEASUREMENT ONLY.** This report does not change what any gate
selects. `hooks/pre-push` and `xtask/src/tasks/ci_scope.rs` are unmodified.
It exists to feed the maintainer's open coverage decision recorded on
[#3985](https://github.com/EffortlessMetrics/perl-lsp-swarm/issues/3985):
should the pre-push shell fast-path's doc-only/single-crate taxonomy be
repointed onto `ci_scope::classify_files`'s taxonomy?

## What this measures

`hooks/pre-push` (the committed shell hook, generated by
`cargo xtask ci-hygiene install-githooks`) and
`xtask/src/tasks/ci_scope.rs`'s `classify_files` are two independent
"changed paths → what to run" classifiers. #3985 Slices 1-3A unified their
**base/diff resolution** (both now share `change_set::resolve_change_set`),
but their **taxonomy** — how a changed-path set maps to a routing decision
— remains separate and, on real inputs, disagrees.

This report runs both classifiers over the same fixed corpus of 11
representative changed-path scenarios and records, per scenario: the
shell's verdict, `ci_scope`'s verdict, whether they agree, and — if not —
which one routes more work ("direction").

- **Shell taxonomy** (`hooks/pre-push` lines 77-206, reproduced as a pure
  function in `xtask/src/tasks/shadow_parity.rs::shell_verdict` — the shell
  script itself is neither invoked nor modified): doc-only glob → skip all
  code gates; else, if every changed path is nested under exactly one
  `crates/<name>/`, run a targeted `cargo fmt/clippy/test -p <name>`; else
  run the full `nix develop -c just pr-fast` gate.
- **Rust taxonomy** (`ci_scope::classify_files`, called unmodified via
  `shadow_parity::rust_verdict`): `diff_class` (`prose_only` /
  `docs_as_code` / `ci_config` / `code` / `mixed`) plus a set of selected
  lanes (`clippy_scoped`, `test_scoped`, architectural-widener lanes like
  `lsp_smoke`/`ux_regression`, and policy lanes like
  `publish`/`security`/`ci_policy`). This report's "touched crates" column
  is the union of every selected lane's `scope` field — the full set of
  crates `ci_scope` would direct *any* proof at for that diff.

## Regenerating this report

```bash
cargo xtask change-set-parity --format markdown
```

The scenario corpus and the **data** in both tables below — `Scenario`,
`Changed paths`, `Shell verdict`, `ci_scope diff_class`,
`ci_scope touched crates`, and `Agreement` — are drawn directly from a live
run of this command (`xtask/src/tasks/shadow_parity.rs`) and are
byte-reproducible: running it again against an unchanged workspace
reproduces those columns exactly. The **`Direction note`** column is
hand-curated commentary layered on top of that data for readability (cross
references between rows, issue citations, and the "matches design intent"
observations below) — it is *not* copy-pasted from the tool's own
(shorter, more mechanical) auto-generated note string. `cargo test -p xtask
shadow_parity` runs the harness's own offline, deterministic unit tests
(fixture `cargo metadata`, no shell-out) that pin the shell-taxonomy
reproduction and the `ci_scope::classify_files` extraction logic that
produces the reproducible columns.

## A second finding: `ci_scope`'s own production call sites disagree

Building this harness surfaced a finding independent of the shell-vs-Rust
question: `ci_scope::classify_files`'s **existing** production call sites
already disagree on `cargo metadata`'s `--no-deps` flag, which changes
whether the reverse-dependency closure is populated at all:

- `ci_scope.rs`'s own `run()` (`cargo xtask ci-scope`) requests the **full**
  resolve graph → reverse-dependency closure is populated.
- `gates::compute_scope_output` and `ci_pr_summary::run` pass `--no-deps` →
  reverse-dependency closure is **always empty** on those call sites today.

This is not a shell-vs-Rust disagreement — it is two production Rust call
sites of the same classifier producing different `touched_crates` sets for
identical input. It matters here because "what does `ci_scope` select" has
two different real answers depending on which call site would eventually
front the pre-push hook. Both tables below are included so the difference
is visible; this report does not recommend which mode a future pre-push
integration should use — that is part of the same maintainer decision.

## Summary

|  | Table 1 (full metadata) | Table 2 (`--no-deps`) |
|---|---|---|
| AGREE | 1 / 11 | 5 / 11 |
| DIFFER (rust broader) | 5 / 11 | 1 / 11 |
| DIFFER (rust narrower) | 5 / 11 | 5 / 11 |
| DIFFER (ambiguous) | 0 / 11 | 0 / 11 |

Key observations for the maintainer's coverage decision (none of these are
recommendations — they are what was measured):

1. **The metadata-mode split dominates the picture.** Under full metadata,
   reverse-dependency closure makes `ci_scope` broader than the shell on
   nearly every single-crate scenario (5/11), because this workspace's
   dependency graph gives even a "leaf" crate like `perl-pod` a wide
   reverse-dependency fan-out (`xtask`, `perllsp`, `perl-lsp-rs`, etc. all
   depend on it transitively). Under `--no-deps` (what the two live
   production call sites actually use today), the same scenarios largely
   **agree** (5/11) — the routine "single crate, small incremental change"
   case matches shell's targeted gate almost exactly.
2. **`workflow-only` and `extension-only` are the cleanest, mode-independent
   coverage-decrease cases**: in both tables, `ci_scope` selects zero
   crate-scoped Rust proof for these, while the shell runs the full
   workspace gate. These match coverage-decision items #1 (shell-vs-`ci_scope`
   routing) and the P4 extension-surface gap already named in #3985's issue
   body, respectively.
3. **`shared-foundation-crate` broadening matches design intent** stated in
   #3985's routing table ("shared foundation: direct package proof now;
   report broader closure") in both metadata modes — this is not a
   surprise disagreement, it is the classifier doing what the issue asked.
4. **Deletions and renames do not introduce a *new* disagreement axis** at
   this taxonomy layer: neither classifier reads git status letters (both
   consume unfiltered `--name-only` output), so they behave identically to
   an add/modify of the same path. The diff-filter question (RIPR's
   `ACMR` → `ACDMRT`) already tracked on #3985 is a separate, resolved-view
   coverage item.

## Non-goals of this report

- Does not change `ci_scope::classify_files` or its callers.
- Does not add a new required CI check.
- Does not resolve the `--no-deps` vs full-metadata split — it documents it.
