## Why 0.15.0 (semver receipt)

PR #221 changed two surfaces in the published `perl-lsp-rs-core::protocol` crate API:

- `JsonRpcRequest.id` / `JsonRpcResponse.id`: `Option<Value>` → `Option<JsonRpcId>`
- `outbound::send_request` parameter: `i64` → `ServerRequestId`

Under 0.x semver those are breaking changes → minor bump. **No wire-protocol change**; `JsonRpcId` serializes identically to the prior `Value`-based IDs for valid shapes.

## Cutover commands (publishing repo)

Run from a clean local checkout with access to both `EffortlessMetrics/perl-lsp-swarm` and `EffortlessMetrics/perl-lsp`.

```bash
# 1. Cross-repo port
cd /path/to/perl-lsp-swarm
git remote add publishing git@github.com:EffortlessMetrics/perl-lsp.git
git fetch origin main
git fetch publishing master

git checkout -b cutover/0.15.0 publishing/master
git merge origin/main --no-ff -m "cutover: import swarm main for 0.15.0 cut"

# 2. Sanity-check before pushing
just version-check                       # → 0.15.0
cargo xtask check-version-sync           # → 44/44 hard sites
bash scripts/check_release_history.sh    # → install-surface clean, release-history clean

# 3. Push to publishing repo
git push -u publishing cutover/0.15.0

# 4. Open the cutover PR (cross-repo head must include the swarm fork prefix
#    if your fork model differs; using cutover/0.15.0 in publishing repo is simplest):
gh pr create \
  --repo EffortlessMetrics/perl-lsp \
  --base master \
  --head cutover/0.15.0 \
  --title "cutover: swarm main → master for v0.15.0 (#224)" \
  --body "$(cat <<'EOF'
Imports swarm main into master as the source-of-truth state for v0.15.0.
See `docs/releases/0.15.0-readiness.md` on the swarm for full context.

Post-merge sequence:
  git checkout master && git pull
  gh workflow run release-orchestration.yml -f version=0.15.0 -f prerelease=false
  # Then the three dispatch-only channels (see below).
EOF
)"
```

## Post-cutover release-orchestration sequence

After the cutover PR merges, dispatch `release-orchestration.yml` from the
publishing repo. Do not create `v0.15.0` by hand first: the orchestration
workflow validates that the tag does not already exist and then creates it.

```bash
# In publishing repo (EffortlessMetrics/perl-lsp):

git checkout master && git pull

gh workflow run release-orchestration.yml \
  -f version=0.15.0 \
  -f prerelease=false \
  -f skip_crates=false \
  -f skip_extension=false \
  -f skip_docker=false
```

## CRITICAL — channel dispatch (don't repeat 0.14.0)

Per [`docs/releases/RELEASE_CLOSEOUT_AUDIT.md`](RELEASE_CLOSEOUT_AUDIT.md), three workflows are `workflow_dispatch` only — they do **not** fire on `release:published`:

| Workflow | Channel |
|---|---|
| `publish-extension.yml` | VS Code Marketplace + Open VSX |
| `docker-publish.yml` | Docker Hub + GHCR |

If these are not explicitly dispatched after the GitHub Release publishes, users on the affected channels silently stay on 0.14.x. This was the root cause of the 0.14.0 closeout failure that left the LSP4IJ bug reporter on 0.13.3.

**Immediately after the GitHub Release publishes**, dispatch them:

```bash
gh workflow run publish-extension.yml -f version=0.15.0
gh workflow run docker-publish.yml    -f version=0.15.0
```

The auto-fire channels (Homebrew, Scoop, Chocolatey) trigger on `release:published` but each opens a downstream tap-repo PR that must be merged before users see the bump:

```bash
gh pr list -R EffortlessMetrics/homebrew-perllsp --state all --limit 5
gh pr list -R EffortlessMetrics/scoop-perllsp    --state all --limit 5
```
